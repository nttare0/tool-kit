# TOOLSTACK — MASTER IMPROVEMENT BLUEPRINT

## Role

Act as a principal software engineer, senior product designer, UX architect, security engineer, SEO engineer, and technical lead with 15+ years of experience shipping production web applications.

You are working on an existing product called **Toolstack**.

Do not treat this as a greenfield application.

Your first responsibility is to understand the existing codebase, architecture, database, routes, components, APIs, authentication, dependencies, and deployment configuration before making structural changes.

Do not blindly rewrite the application.

Preserve working functionality unless there is a clear reason to replace it.

The objective is to transform Toolstack from a basic software/tool directory into a **high-quality software discovery and decision platform**.

---

# 1. PRODUCT THESIS

The current product concept is:

> “A field guide to useful tools.”

The improved product thesis should be:

> **Toolstack helps people discover the software worth using, understand its tradeoffs, compare alternatives, and assemble the right stack for the job.**

Do NOT build another generic directory whose primary experience is:

> search → cards → click external link

The product should instead help users answer:

> “What should I use for this?”

and:

> “Why should I choose this instead of the alternatives?”

Toolstack should compete through:

* curation
* trust
* useful editorial information
* task-oriented discovery
* comparisons
* alternatives
* workflow stacks
* strong UX
* high-quality tool detail pages
* excellent search and SEO
* reliable metadata
* security
* performance

Do not attempt to compete purely on number of listed tools.

# 3. NON-NEGOTIABLE IMPLEMENTATION RULE

For every feature you change:

1. inspect existing behavior
2. identify dependencies
3. make the smallest safe architectural change
4. implement it
5. run tests
6. run type checking
7. run linting
8. test the affected routes
9. verify accessibility
10. verify responsive behavior
11. verify security implications
12. verify production build

# 30. SECURITY HEADERS

Implement a deliberate security-header policy.

Evaluate:

* Content-Security-Policy
* Strict-Transport-Security
* X-Content-Type-Options
* Referrer-Policy
* Permissions-Policy
* frame-ancestors through CSP
* appropriate cache controls

Do not copy a random header configuration from the internet.

Ensure the CSP actually matches the application's scripts, images, fonts, APIs, analytics, and third-party services.

Use CSP as defense in depth, not as a replacement for fixing XSS. OWASP specifically recommends security response headers and CSP for mitigating classes of browser-side attacks.

# 56. SECURITY TEST CASES

Create automated tests for cases such as:

### Authorization

Attempt to access another user's resource by changing an ID.

Expected:

`403` or `404`, depending on the API's information-disclosure design.

### Admin

Attempt admin actions as a normal user.

Expected:

Access denied server-side.

### XSS

Submit malicious HTML/script through any user-editable field.

Expected:

The payload is safely rendered as text or sanitized content.

### Open redirect

Attempt:

`/go?url=https://evil.example`

Expected:

Rejected.

### SSRF

Attempt to make server-side metadata fetching access:

* localhost
* loopback
* private IPs
* internal service names

Expected:

Rejected.

### Rate limiting

Send repeated authentication or expensive API requests.

Expected:

Rate limit enforced.

### Secret exposure

Search client bundle and responses for server-side secrets.

Expected:

No secrets.
